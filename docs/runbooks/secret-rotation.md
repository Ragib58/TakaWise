# Runbook — Secret Rotation

Secrets live in the cloud secret manager (AWS Secrets Manager or SSM) and are injected as environment variables. They are never stored in git, images or `NEXT_PUBLIC_*`. Rotate them on a schedule (every 90 days), **immediately** when someone with access leaves, and on any suspected leak.

| Secret                  | Effect of rotation                                 | Procedure                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------- | -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `JWT_ACCESS_SECRET`     | Access tokens are signed with it (15 min lifetime) | **Zero-downtime:** (1) set `JWT_ACCESS_SECRET_PREVIOUS` = the current value and `JWT_ACCESS_SECRET` = a new random value of at least 32 characters; (2) deploy, so new tokens use the new key while old tokens still verify; (3) after ≥ 15 min (`ACCESS_TOKEN_TTL_SECONDS`), remove `JWT_ACCESS_SECRET_PREVIOUS` and deploy again. **On a leak**, skip step 1's previous key: every access token then fails and users silently refresh |
| `AUTH_HMAC_SECRET`      | Keys OTP hashes and IP pseudonyms                  | Replace and deploy. Codes that are currently pending become invalid, so users request new ones. Audit IP hashes before and after rotation cannot be linked. Must differ from the JWT key                                                                                                                                                                                                                                                |
| Refresh tokens          | Opaque values; only their SHA-256 is stored        | No key to rotate. To force everyone to sign in again: `UPDATE sessions SET revoked_at = now(), revoked_reason = 'LOGOUT_ALL' WHERE revoked_at IS NULL;` (reviewed SQL, run during an incident)                                                                                                                                                                                                                                          |
| `DATABASE_URL` password | DB access                                          | Create a new DB user/password (or use RDS rotation). Update the secret, roll the API, then drop the old credential                                                                                                                                                                                                                                                                                                                      |
| `REDIS_URL` auth        | Jobs and rate limits                               | Update the ElastiCache auth token (it supports two tokens during rotation), roll the API, then remove the old token                                                                                                                                                                                                                                                                                                                     |
| `SMTP_URL`              | Email delivery                                     | Create a new provider credential, update the secret, roll the API, revoke the old one                                                                                                                                                                                                                                                                                                                                                   |
| `METRICS_TOKEN`         | Prometheus scrape                                  | Update the scraper config and the secret together                                                                                                                                                                                                                                                                                                                                                                                       |

## Checklist after a suspected leak

1. Rotate the affected secret, with no grace period.
2. Revoke sessions if auth secrets were involved (SQL above).
3. Search the audit logs for unusual access during the exposure window: `auth.login.*`, `auth.refresh.reuse_detected`, `export.transactions`.
4. Record a timeline in the incident ([incident-response.md](incident-response.md)).
